# Контракт frontend → backend → AI

## HTTP

`GET /` отдаёт `frontend/index.html`; `/app.js` и `/styles.css` — файлы интерфейса. Все запросы frontend используют относительные пути на том же адресе. Swagger остаётся на `/docs`.

`GET /api/options` возвращает `cities`, `categories`, `event_types`, `languages` (массивы точных значений из БД), `date_min`, `date_max` (ISO-даты включительно) и `dataset_version`. Старого `calendar_window` нет. Значения справочника не означают, что любая комбинация города, категории и даты найдёт кандидатов.

`POST /api/recommendations`:

```json
{
  "city": "Алматы",
  "date": "2026-10-10",
  "event_type": "корпоратив",
  "category": "Ведущий",
  "budget_kzt": 1000000,
  "duration_hours": null,
  "language": null,
  "preferences": "Деловой корпоратив"
}
```

Бюджет — целое положительное число до `9007199254740991`, длительность — конечное положительное число или `null`; пожелания — строка до 1000 символов, по умолчанию пустая. Пробелы в начале и конце строк удаляются; регистр справочников сохраняется. Неизвестные поля запрещены. Язык и длительность можно не передавать. Неверный тип/справочник/дата возвращает HTTP 422 с `detail: [{loc: ["body", "поле"], msg, type, ...}]`. Недоступная БД — 503, не пустой результат подбора.

Ответ всегда содержит:

| Поле | Значение |
| --- | --- |
| `status` | `matched`, `category_absent` (нет пары город+категория) или `no_matches` (пара есть, но условия не пройдены) |
| `message` | Понятный текст результата |
| `cards` | Карточки в готовом порядке; для пустой выдачи `[]` |
| `total_in_city_category` | Число профилей до остальных строгих фильтров |
| `eligible_count` | Число прошедших все строгие фильтры |
| `excluded_counts` | `date`, `budget`, `event_type`, `duration`, `language`; каждый профиль учитывается только в первой причине в этом порядке |
| `selection_mode` | `ai` / `fallback`; для пустой выдачи `null` |
| `cache_hit` | Получен ли ранее сохранённый ответ |
| `dataset_version` | Версия каталога PostgreSQL |
| `recommendation_version` | Версия правил, модуля, модели, prompt и настроек |

Карточка: `id`, `name`, `categories: string[]`, `city`, `price_from_kzt: number`, `reason`, `evidence_ids: string[]`, `synthetic: boolean`, `city_imputed: boolean`, `price_imputed: boolean`. `name` берётся из `contractors.anon_name`; в БД столбец сохраняет своё имя. Технический маршрут `GET /api/contractors/{id}` по-прежнему отдаёт исходный профиль с `anon_name` и всеми 13 полями.

Frontend **не сортирует** карточки. Метка резервной выдачи: **«Резервный подбор · без AI»**. В этом режиме порядок по цене, затем ID; пожелания не оцениваются. Если AI-модуль возвращает свой fallback, он тоже обязан ставить `selection_mode=fallback`.

## Интерфейс AI-модуля

Backend уже импортирует и типизирует CSV средствами PostgreSQL. Для работающего приложения повторный CSV-парсер не нужен. Модуль участника 2 получает готовые профили из БД:

```python
async def rank_candidates(request: dict, eligible_candidates: list[dict]) -> dict:
    ...
```

`request` совпадает с JSON выше. Вход отсортирован по ID для постоянного порядка передачи, но содержит **всех** допустимых кандидатов без лимита 3. Каждый кандидат содержит все исходные поля: `id`, `anon_name`, `categories`, `city`, `city_imputed`, `synthetic`, `price_from_kzt`, `price_imputed`, `event_formats`, `languages`, `max_hours`, `busy_dates`, `description`, а также alias `name` и словарь `evidence`. Списки разобраны; цена — `int`, `max_hours` — `float | None`, даты — ISO-строки, флаги — `bool`, описание полное. Модуль не должен менять правила допуска по пожеланиям пользователя.

Результат:

```json
{
  "selection_mode": "ai",
  "selected": [
    {
      "id": "<ID из переданных кандидатов>",
      "reason": "1–2 предложения с объяснением на основе фактов профиля и контекста.",
      "evidence_ids": ["<ключ из evidence этого профиля>"]
    }
  ]
}
```

Пример показывает структуру одного элемента; `selected` должен содержать **ровно `min(3, len(eligible_candidates))`** уникальных допустимых ID в порядке рекомендаций. `reason` — непустая строка до 4000 символов. `evidence_ids` — непустой список уникальных ключей фактов выбранного профиля. Не добавляйте поля имени/цены в результат: backend собирает их из БД. Для пустого допустимого списка модуль не вызывается.

### Факты

По умолчанию используется `app.ranking.build_evidence(candidate)`:

- `{id}:city`, `{id}:categories`, `{id}:price_from_kzt`, `{id}:event_formats`, `{id}:languages`, `{id}:max_hours`, `{id}:busy_dates` — структурированные факты;
- `{id}:description:1`, `{id}:description:2`, … — последовательные фрагменты полного описания, разделённые по границам предложений/строк.

`candidate["evidence"]` уже содержит этот словарь `ID → текст`. Модуль может экспортировать собственную детерминированную синхронную функцию `build_evidence(candidate) -> dict[str, str]`; тогда backend использует именно её для подготовки входа и проверки ссылок. Функция не должна ходить в сеть или возвращать выдуманные факты. ID должны воспроизводиться для одного профиля.

Backend проверяет существование и принадлежность ссылки, но это **не семантическая проверка** того, что объяснение следует из цитаты. За качество объяснений отвечает AI-модуль и совместная проверка реальных примеров. Описания и пожелания нужно передавать модели как данные, не как инструкции, меняющие системные правила.

### Ошибки, таймаут и версии

`AI_MODULE` задаёт импортируемый путь (для включённого в репозиторий пакета — `ai_module`), `AI_TIMEOUT_SECONDS` — таймаут 5 секунд по умолчанию, допустимо `(0, 30]`. `rank_candidates` должна быть асинхронной и не блокировать event loop. Можно реализовать fallback внутри модуля; backend также страхует исключения, таймаут и неверный ответ своим резервным подбором. Секреты, полные payload и тексты исключений модели не пишутся в лог адаптера.

Модуль, его зависимости и секрет API остаются на сервере. Если модуль экспортирует строковую `RECOMMENDATION_VERSION`, backend автоматически включает её в ключ кэша; её нужно менять вместе с prompt, схемой фактов или алгоритмом. `AI_VERSION` остаётся дополнительной ручной меткой, в том числе для модулей без экспортируемой версии. Полный проверенный ответ сохраняется; старый fallback не заменяется AI-ответом внутри той же версии. При сбое PostgreSQL ответ не считается сохранённым и возвращается ошибка сервиса.

Модуль `ai_module` версии `ranking-v6:evidence-v3:fallback-v2` возвращает объяснения
до 280 символов: предложение о свободной дате по результату фильтра backend и
предложение с одной-двумя цитатами профиля. `evidence_ids` относятся к цитатам;
достоверность даты обеспечивается строгими фильтрами до вызова модуля.
