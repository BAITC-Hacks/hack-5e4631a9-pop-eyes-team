# AI-модуль: подключение для участника 1

```python
from ai_module import build_evidence, rank_candidates, RECOMMENDATION_VERSION

result = await rank_candidates(request, eligible_candidates)
```

Python 3.11+. Зависимости перечислены отдельно в `requirements-ai.txt`:

```console
python -m pip install -r requirements-ai.txt
```

Общий `requirements.txt` включает `-r requirements-ai.txt`; Dockerfile копирует
пакет `ai_module`, а Compose передаёт четыре настройки AI в контейнер приложения.
Модуль не читает CSV, не подключается к БД, не фильтрует кандидатов и не сохраняет
результаты. Backend передаёт всех прошедших строгие фильтры кандидатов.

## Вход и выход

`request`: словарь по согласованному API или Pydantic v2-модель
(`model_dump(mode="json")`). В словаре дата может быть ISO-строкой или `datetime.date`.

Каждый кандидат — словарь с полями `id`, `anon_name`, `city`, `categories`,
`price_from_kzt`, `event_formats`, `languages`, `max_hours`, `description`,
`synthetic`, `city_imputed`, `price_imputed`. Числа, списки, bool и NULL уже
разобраны backend. Цена — целое число; описание — полный текст.

```json
{
  "selection_mode": "ai",
  "selected": [
    {
      "id": "DEMO-02",
      "reason": "Объяснение выбора на основе профиля и контекста.",
      "evidence_ids": ["DEMO-02:description:1"]
    }
  ]
}
```

Это пример формы ответа с тестовым ID. В реальном ответе всегда
`min(3, len(eligible_candidates))` элементов; порядок модели сохраняется.
Внутри вход сортируется по ID только для стабильного порядка передачи.
Все данные профиля, включая полный текст описания, представлены в `evidence`.

При пустом входе возвращается `{"selection_mode": "fallback", "selected": []}`
без обращения к сети. Обычно backend обрабатывает `category_absent` и
`no_matches` до вызова AI; пустой результат не следует показывать как сбой AI.

## Общие факты

```python
by_id = {candidate["id"]: candidate for candidate in eligible_candidates}
for item in result["selected"]:
    facts = build_evidence(by_id[item["id"]])
    assert all(ref in facts for ref in item["evidence_ids"])
```

`build_evidence(candidate)` возвращает `{evidence_id: текст}`. Структурированные
поля имеют ID `<id>:field:<поле>`, фрагменты описания — `<id>:description:<номер>`.
Разбиение выполняет код по переносам строк и пробелам после `.`, `!`, `?`.
Содержательный текст не обрезается; пробелы нормализуются. Это фрагменты текста,
а не лингвистически идеальное разбиение на предложения.

При неизменном профиле результат детерминирован. При изменении описания ID могут
сместиться, поэтому `dataset_version` входит в ключ сохранённого решения.
Существование ссылки подтверждает источник, но не истинность любого пересказа:
качество объяснений нужно проверить на реальных профилях.

В AI-ответе допускается 1–3 ссылки на карточку. Если у выбранного кандидата есть
непустое описание, хотя бы одна ссылка должна вести на фрагмент этого описания:
ссылки только на имя, город и категорию не принимаются. Это необходимая проверка
источника, а не автоматическое доказательство смысла каждого утверждения.

## Конфигурация и ошибки

Переменные окружения сервера:

| Переменная | Значение по умолчанию |
| --- | --- |
| `OPENAI_API_KEY` | Пусто: резервный режим |
| `OPENAI_MODEL` | `gpt-4o-mini` |
| `AI_MODE` | `auto`; для принудительного резерва — `fallback` |
| `AI_TIMEOUT_SECONDS` | `5` |

При реальной проверке на четырёх синтетических профилях ответ занял около
6,9 секунды: лимит 5 секунд приводил к fallback. Для текущего локального demo
в `.env` выставлено `AI_TIMEOUT_SECONDS=8`. Это замер одного успешного ответа,
а не гарантия задержки: после подключения реальных профилей измерить снова.

Загрузку `.env` выполняет приложение или Compose (явный список `environment`). Сам пакет
файлы окружения не читает. Ключ хранится в исключённом из Git `.env`, а не в
`.env.example`. Вызов модели выполняется только на сервере.

Один асинхронный запрос через OpenAI Responses API, Structured Outputs, без
автоматических повторов SDK. Общий лимит ожидания сетевого вызова —
`AI_TIMEOUT_SECONDS`; подготовка входа и локальные проверки выполняются отдельно.
Формат сверён с [официальной документацией OpenAI](https://developers.openai.com/api/docs/guides/structured-outputs).

При ошибке API, таймауте, отказе модели, неполном JSON, неправильном количестве,
неизвестных/повторных ID, пустых объяснениях или чужих evidence возвращается
`selection_mode="fallback"`. Резерв: цена по возрастанию, затем ID; объяснения
строятся из структурированных полей, подставленные значения отмечаются.
Предупреждение в логах содержит только класс ошибки, без ключа и содержимого запроса.
Отмена запроса вызывающей стороной распространяется наверх.

Неверные входные данные/настройки — ошибки интеграции, не штатный fallback
(`ValueError`, `KeyError` или `TypeError`). Backend всё равно повторно проверяет
допуск, количество, уникальность и evidence перед сохранением.

UI при fallback: «AI-подбор временно недоступен; показаны подходящие варианты
по начальной цене».

## Сохранение и версии

Экспортируются `PROMPT_VERSION`, `EVIDENCE_VERSION`, `RECOMMENDATION_VERSION`.
Backend включает `RECOMMENDATION_VERSION`, `OPENAI_MODEL`, версию датасета,
свои правила отбора и весь запрос (включая дату и preferences) в ключ решения.
Сначала читает кэш; при промахе вызывает модуль и атомарно сохраняет результат
до выдачи. Сохраняются и AI, и fallback, без скрытой замены после восстановления API.
Изменения инструкции, разбиения evidence и fallback требуют обновить версии.

## Проверка

Offline-тесты не используют ключ и не обращаются к API:

```console
python -m unittest discover -s tests -p "test_ai_module.py" -v
```

Ручная проверка после загрузки переменных окружения:

```console
python -m ai_module.smoke --require-ai
```

Для локального PowerShell можно загрузить только настройки AI из `.env`,
не выводя ключ и не выполняя содержимое файла как команды:

```powershell
foreach ($line in Get-Content -LiteralPath .env -Encoding UTF8) {
    if ($line -match '^\s*(OPENAI_API_KEY|OPENAI_MODEL|AI_MODE|AI_TIMEOUT_SECONDS)\s*=\s*(.*?)\s*$') {
        $name = $Matches[1]
        $value = $Matches[2].Trim().Trim([char]34).Trim([char]39)
        [Environment]::SetEnvironmentVariable($name, $value, 'Process')
    }
}
$env:PYTHONIOENCODING = 'utf-8'
.\.venv\Scripts\python.exe -m ai_module.smoke --require-ai
```

Этот пример рассчитан на простые строки `ИМЯ=значение`, как в `.env.example`,
без многострочных значений и комментариев на той же строке, что и ключ.

По умолчанию используются четыре **синтетических тестовых профиля**, не исходный
датасет. Вывод содержит режим, время, выбранные ID, объяснения и evidence.
`--require-ai` завершает проверку с ошибкой при fallback, чтобы его нельзя было
принять за успешный вызов модели.

Для проверки на реальных профилях backend экспортирует JSON с ключами `request`
и `eligible_candidates` (уже после фильтров):

```console
python -m ai_module.smoke --input path/to/eligible.json --require-ai
```

Контрольный запрос: Алматы, Ведущий, корпоратив, 2026-10-10, бюджет 1000000;
по аудиту должны пройти четыре профиля. Демо на синтетических данных подтверждает
транспорт и контракт; качество на каталоге и сохранение в БД проверяются отдельно
совместно с backend.
