# Проверка AI-модуля на реальном каталоге

Проверка выполнена 23.09.2026 отдельно от backend и Docker.
Модель: `gpt-4o-mini`; версия: `ranking-v5:evidence-v3:fallback-v1`;
таймаут одного вызова — 8 секунд, повторов SDK нет.

## Итоговый прогон

Семь непустых сценариев получили `selection_mode=ai`, без fallback и ошибок
автоматических проверок. Два пустых сценария вернули пустой список без вызова API.
Проверены количество `min(3, eligible_count)`, уникальность и допустимость ID,
ссылки на факты и заданные ниже критерии контекстного выбора.

| Сценарий | Кандидатов | Порядок AI | Секунды |
| --- | ---: | --- | ---: |
| Деловой корпоратив, 10 октября | 4 | HK-27222 → HK-77838 → HK-88430 | 3,823 |
| Развлечения и танцы, 10 октября | 4 | HK-29829 → HK-27222 → HK-88430 | 2,639 |
| Без пожеланий, 10 октября | 4 | HK-27222 → HK-77838 → HK-88430 | 2,874 |
| Ведущие, 14 ноября | 4 | HK-27222 → HK-44923 → HK-44733 | 2,860 |
| Ведущий, 19 декабря | 1 | HK-35215 | 1,557 |
| Флорист, 10 октября | 1 | HK-39372 | 3,544 |
| Площадки, 14 ноября | 2 | HK-90011 → HK-64395 | 1,774 |
| Ведущий, бюджет 10 000 ₸ | 0 | Пусто, без AI | 0,001 |
| Декоратор в Астане | 0 | Пусто, без AI | 0,001 |

Для семи AI-вызовов: минимум 1,557 с, максимум 3,823 с, медиана 2,860 с.
Это один небольшой последовательный прогон с локального компьютера; он не
доказывает стабильную задержку, процентиль или время полного HTTP-запроса.
Новые вызовы могут вернуть другой порядок. Повторяемость для пользователя
обеспечит сохранение решения backend, а не детерминизм модели.

Принудительный fallback прошёл все девять сценариев: порядок совпадает с
[аудитом данных](DATA_AUDIT.md), время около 0,001 с на сценарий в этом прогоне.
Пустые бизнес-исходы различает backend; сам AI-модуль не возвращает `status`.

## Критерии и ручная проверка смысла

Критерии относятся только к этим тестовым запросам, не встроены в рабочее
ранжирование как правила выбора конкретных ID:

- Для делового контекста профили с интеллектуальной/ненавязчивой подачей должны
  быть выше профиля, описывающего прежде всего танцы и развлечения. Не задаём
  единственный правильный порядок среди трёх подходящих ведущих.
- Для явного приоритета танцев первым ожидается HK-29829 (Аня Форджер): профиль
  прямо говорит о развлечениях, танцах и отсутствии длинных речей.
- Для площадки на 180 гостей с кейтерингом и парковкой первым ожидается HK-90011:
  эти свойства указаны в профиле, вместимость — до 200 гостей.

Ручная проверка итоговых цитат:

- Деловой запрос выделяет опыт и тонкий юмор Сон Гоку, ненавязчивую подачу Хаула,
  деловые встречи и интеллигентный юмор Куррапики. Куррапика имеет наиболее явную
  формулировку делового опыта, но модель поставила его третьим: конкретный порядок
  остаётся субъективной оценкой, а не доказанным оптимумом.
- В танцевальном запросе первое место Ани подтверждено прямыми цитатами; остальные
  ведущие описаны через динамику и стиль, не через выдуманный опыт танцевальных шоу.
- У Кики процитированы юмор и персональный подход; у флориста — авторское оформление
  и примеры клиентов. Это утверждения исходного профиля, не внешняя проверка отзывов.
- Для второй площадки HK-64395 вместимость, кейтеринг и парковка **не подтверждены**:
  её цитаты описывают вид и атмосферу. Нельзя трактовать сам факт включения в выдачу
  как выполнение этих пожеланий. По контракту при двух допустимых кандидатах
  модуль возвращает обоих; пожелания — мягкие условия. Если вместимость станет
  обязательной, её нужно добавить в структурированные данные и фильтры backend.

Фактический текст объяснений теперь собирается из исходных цитат. Автоматически
проверяется происхождение, но не смысловая полнота соответствия каждому пожеланию.
Для production потребуются более широкая оценка качества и работа с неподтверждёнными
пожеланиями; текущая проверка ограничена предоставленным каталогом и MVP.

## Найденные проблемы и исправления

1. PostgreSQL возвращает `max_hours` как `Decimal`; прежняя JSON-сериализация
   ломалась на 57 из 66 SQL-подобных профилей. Общая нормализация теперь принимает
   `Decimal` и даёт те же факты, что JSON с `float`. Проверены все 66 записей.
2. В исходном пробном ответе модель поставила акцент на танцах выше подходящего
   деловому контексту профиля и написала о возможном превышении бюджета уже
   допустимым кандидатом. Уточнены приоритеты prompt; свободный фактический пересказ
   заменён цитатами с проверяемыми ссылками.
3. Длинные списки услуг вызывали fallback из-за лимита цитат. Они разбиваются
   на короткие фрагменты без потери содержательного текста; проверены все описания.
4. Переписывание фрагмента запроса и выбор общих полей вместо описания иногда
   приводили к отклонению ответа. Теперь схема ограничивает выбор ID профилей,
   их фактов и фрагментов запроса. Код повторно проверяет ответ.
5. Метки полного/частичного совпадения модель назначала непоследовательно.
   Они убраны; в карточку передаются цитаты без такой недоказанной оценки.
6. Контрольная сумма тестового источника отличалась при LF/CRLF. Для фикстур
   используется `source_sha256_lf`, нормализующая только переносы строк.
   Схема SQL-импорта и её контрольные суммы не изменялись.

Промежуточные сбои не включены в статистику итоговой версии: во время доработки
были fallback по невалидным ответам. Итоговые семь успешных вызовов не доказывают,
что модель больше никогда не ошибётся; отказоустойчивость остаётся обязательной.

## Локальные проверки и границы

35 тестов `test_ai*.py` проверяют контракт, SQL-типы, сохранение текста всех 66
описаний, воспроизводимость фикстур и переносов строк, таймаут с отменой вызова,
отмену вызывающей задачи, ответы SDK через подменённый HTTP transport,
ошибки 401/429/500, отказ/неполный JSON, неизвестные/повторные ID, чужие ссылки,
подмену свободного текста, fallback и сохранение порядка.

Проверка prompt injection моделирует попытку вернуть посторонний ID и подтверждает
его отклонение. Это не полноценный состязательный тест устойчивости модели.
Зависимости не расширены; API-ключ в артефакты не включается.

Docker в текущем окружении недоступен. Реальная БД, SQL-фильтры, HTTP-endpoint,
кэш, одновременные запросы и UI этим прогоном **не проверены**. Нормализация
SQL-типов проверена на строках, построенных из каталога, без соединения с PostgreSQL.
